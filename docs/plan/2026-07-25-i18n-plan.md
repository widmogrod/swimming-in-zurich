# Internationalization — pl / en / de / it / fr

## Context

The app is monolingual by accident, not by design, and it is **already inconsistent**: the UI
chrome is hardcoded English while every byte of data flowing through it is German. The same
`StatusOut.detail` field renders both — `Closed · schedule not yet curated` (English, from
`domain/query.py:454`) and `Closed · Sommerpause` (German, verbatim from
`data/pools/city.yaml:44`). Fixing that mixed-language seam is the actual work; picking a
message library is the easy part.

There is **zero i18n infrastructure today**: no gettext, no Babel, no `Accept-Language`
negotiation, and — notably — **not a single `Intl.*` call anywhere in the UI**. All date, number
and plural formatting is hand-rolled English.

### Two structural assets already in place

1. **The domain already carries machine keys next to every prose string.** `AccessInfo.key`,
   `EligibilityResult.rule`, `StatusOut.status`, `ELIG_IN/CHK/NO`, `STATE_CLOSED/UNLISTED/NONE`,
   and `legendModel()`'s family keys are a ready-made message-id namespace. We are not inventing
   an id scheme; we are exposing one that exists.
2. **`legend.test.js` already asserts on keys, not labels.** That is the migration model for
   every other test.

### Two structural hazards

1. `blocks/board.js:115-120` builds `"Mon · 20 Jul"` by **splitting `formatLabel()` output on
   spaces** (`parts[0]`, `parts[1]`, `parts[2]`). It breaks silently for any locale whose date
   is not exactly three space-separated tokens. This is a latent bug independent of i18n.
2. `blocks/insightbar.js` composes whole sentences by concatenating 3–5 fragments, e.g.
   `` `${lead} · best public window ${a}/${b} at ${facility} ${start}–${end}` ``. Concatenated
   sentences cannot be word-order-translated. This is the largest single chunk of real work.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| **Runtime** | **Hand-rolled on native `Intl`** (~150–250 lines with tests) | No bundler exists (`tsc` → `dist/`, raw `<script type=module>`), so any npm runtime must be vendored. `Intl.PluralRules` already yields correct CLDR Polish `one/few/many/other` in every engine — a library buys *message syntax*, not plural correctness. DIY gives a literal key union for free and adds zero vendored bytes. |
| **Data scope** | **UI + bounded data sets only** | Translate the ~150 UI strings plus the small closed sets. **Do not** translate the 57 scraped German `description` blocks in `catalog.json` — they are re-scraped upstream, so translating them creates a permanent liability where every refresh silently invalidates 5 locales. |
| **Locale delivery** | **Cookie (canonical) + localStorage (mirror)** | Explicit product decision. The cookie is load-bearing: it is the only channel the server can read. See the trade-offs recorded below. |
| **Catalog format** | **Typed `.ts` modules, one per locale** | **Reversed from JSON — see below.** Required by both the build pipeline and the compile-time Polish guarantee. |
| **Server prose** | **Eliminated — API returns keys + params** | Collapses to one catalog and one completeness gate instead of parallel Python and JS i18n stacks. |

### Reversed decision: catalogs are `.ts`, not `.json`

The first draft specified JSON catalogs. **That does not build, and it defeats the plan's own
enforcement mechanism.** Recorded rather than silently edited, because the JSON rationale (TMS
compatibility) was real and is being traded away deliberately.

- **It never reaches the browser.** The build is `tsc -p tsconfig.json` and nothing else — no
  `resolveJsonModule` in the tsconfig, no copy step in `package.json`, and `main.py:127` runs only
  `npm run build`. `tsc` emits `.js`; a `locales/pl/app.json` would sit in the source tree and
  never appear in `dist/`.
- **It defeats the Polish guarantee.** `keyof typeof en` and `Plural<L>` are compile-time
  constructs. They require a module the type-checker sees, not a payload fetched at runtime.
- **It has a dual-path hazard.** `main.py:131` notes `TestClient` serves the *source* `/static/js`
  tree while production serves `dist/`; a runtime `fetch()` of a catalog would have to resolve
  correctly under both.

So: `locales/<locale>.ts`, each exporting a typed const, compiled into `dist/` like every other
module. No fetch, no copy step, full type-checking.

**What this costs:** direct TMS ingestion. Per the workflow section there is no TMS initially, and
when one arrives a `.ts` ↔ `.json` export/import script is a small, well-understood piece of work.
Revisit this decision at that point, not before.

### Recorded trade-off: cookie-only locale

Cookie/localStorage-only means there is **no unique URL per locale**. Consequences, accepted:

- Search engines index one version only; there is no meaningful multilingual SEO.
- A user cannot share a link in a chosen language.
- `hreflang` is not applicable.

**The cookie is canonical, not localStorage.** `_SHELL` is server-rendered and must emit
`<html lang>`, and the server cannot read localStorage. localStorage is a convenience mirror for
the client only; any disagreement resolves in favour of the cookie.

**First-paint flash:** the shell is served with the cookie's locale, so markup is correct from the
first byte. But if a user's stored locale is absent (first visit) the server negotiates from
`Accept-Language`, and a later explicit choice must write the cookie *and* re-render — not merely
re-translate the DOM, or `<html lang>` goes stale. Simplest correct behaviour: a locale change sets
the cookie and reloads.

**Mitigation (required, not optional):** locale resolution lives behind **one seam** —
`resolveLocale()` client-side and a single `locale` dependency server-side. Adding `/{locale}/`
path prefixes later must be a routing change plus a new resolver branch, never a rewrite of call
sites. No module outside that seam may read the cookie directly.

### Why not the alternatives

- **Do not wait for native `Intl.MessageFormat`.** The MF2 *format* is stable (CLDR 47, Mar 2025),
  but the *JS API* is stuck at **TC39 Stage 1** — the champions say so publicly. No engine ships
  it. ICU MessageFormat 1 remains the 2026 default; revisit ~2028.
- **Polyglot.js** — non-CLDR plurals, actively wrong for Polish.
- **Fluent** — no `@fluent/bundle` release in over 12 months; `.ftl` also cuts us off from most
  TMS tooling.
- **typesafe-i18n** — best types available, but in caretaker maintenance.
- **Lingui / Intlayer** — compile-time macros require babel/SWC. Incompatible with a `tsc`-only build.
- **i18next** — the correct answer *if* we wanted to buy (13.5 kB gz, zero deps, vendorable). Kept
  as the documented fallback if the hand-rolled runtime proves insufficient; the message-key
  namespace below is deliberately i18next-compatible so the swap stays cheap.

## Slices

**Sequencing principle: every slice ships a working app.** No slice may remove a text source before
its replacement renders. This is why S2 is additive and the wire prose is not deleted until S5 —
the first draft stripped prose in S2 and only taught the client to render codes in S3, which left
the app broken across the designated pause point.

### S1 — the runtime + the `Intl` cleanup *(pause here)*

Build `static/js/i18n.ts`: `t(key, params)` with `{placeholder}` interpolation, plural-category
lookup via `Intl.PluralRules`, and `resolveLocale()` (the single seam). Types come from the `en`
catalog module — a wrong key is a compile error, no codegen needed.

Simultaneously kill the formatting debt, because it is what makes the catalog honest:

- Delete both weekday tables (`api.js:49`, `datestepper.js:6`) → `Intl.DateTimeFormat`.
- **Delete `weekdayDateLabel()`'s space-splitting** (`board.js:115-120`) — consume
  `Intl.DateTimeFormat.prototype.formatToParts()` and read the named parts, never re-parse a
  formatted string.
- Dedupe the three `mondayOf()` copies (`toolbar.js:24`, `api.js:34`, `urlstate.ts:78`).
- `Intl.NumberFormat` for `km` / `°C` (de/fr/it/pl all use `,` as the decimal separator).
- `Intl.DateTimeFormat` for the raw ISO dates in `detailpanel.js:292` and `provenancestamp.js:22`.

**This slice is user-visible, despite touching no copy.** `formatLabel()` currently yields
`'Thu 23 Jul'`; `Intl.DateTimeFormat('en-GB', …)` yields `'Thu, 23 Jul'` — a comma. Every date in
the UI changes, and the assertions in `header.test.js:62,65` (`'Week of Mon 20 Jul'`) and the
datestepper suites break.

**Decision: accept the `Intl` output and update the tests.** Reassembling `formatToParts()` to
preserve the exact legacy string is possible but would re-introduce, in a new form, precisely the
locale-fragile format-pinning this slice exists to delete. The comma is correct for `en-GB`.

Gate: the hand-rolled runtime must clear `crap_ts.mjs`. It is the highest-complexity new module in
the UI, so it needs proportionate tests — that is the accepted cost of building rather than buying.
Pause and confirm the app renders before proceeding.

## Rollout order

A locale ships only when its catalog is complete and reviewed. The enforcement is structural rather
than procedural: **the locale switcher is generated from the set of complete catalogs**, so a
partial locale is unreachable by users — there is no way to "temporarily" expose one.

| Order | Locale | Gate |
|---|---|---|
| 1 | `en` | Source locale, authored in S3 |
| 2 | `de` | Highest-value for Zürich; also the language the underlying data is already in |
| 3 | `fr`, `it` | MT first pass + review |
| 4 | `pl` | MT first pass + **native review sign-off** (see "Polish cannot be broken" §7) |

`pl` is deliberately last. It is the locale with the hardest correctness bar, and putting it last
means the runtime, the catalog shape, and the plural machinery have all been exercised by three
other locales before it is authored — so a `pl` bug is a `pl` bug, not an infrastructure bug
discovered late.

## Auditability

The project idiom already exists: `REPRESENTATIVE_ACCESS` plus a completeness test asserting every
union member has an entry — "a silent gap the compiler cannot see" made visible. Apply exactly
that to catalogs.

| Gap | Gate |
|---|---|
| A hardcoded string is added to source | `eslint-plugin-i18next` `no-literal-string`, `mode: 'all'`, `ignoreCallee: ['t']` |
| A key is used in code but missing from a catalog | `keyof typeof en` — compile error, free |
| A locale file is missing keys the others have | key-parity test (all 5 catalogs have identical key sets) |
| **A `pl` plural key is missing a category** | **compile error** — see "Polish cannot be broken" |
| A translation silently dropped `{pool}` | placeholder-parity test |
| Every domain union member has a message | completeness test, `REPRESENTATIVE_ACCESS` pattern |
| A string is rendered but never externalized | **pseudolocale smoke pass** |

## Polish cannot be broken

This is a hard constraint, not a quality target. Polish is the most grammatically demanding of the
five locales and the one where a subtle break is invisible to everyone reviewing the diff. A gate
that must be *remembered* is not sufficient — the enforcement has to be structural.

### 1. Plural completeness is a compile error, not a test

The single biggest advantage of the hand-rolled runtime: **we own the catalog types.** A plural
message is not a string, it is a record keyed by the categories that locale actually uses. (This is
the mechanism the `.ts`-catalog reversal exists to protect — it cannot work on fetched JSON.)

```ts
// The categories each locale uses, verified against the platform (see §2).
const PLURAL_CATEGORIES = {
  en: ['one', 'other'],
  de: ['one', 'other'],
  fr: ['one', 'many', 'other'],
  it: ['one', 'many', 'other'],
  pl: ['one', 'few', 'many', 'other'],
} as const satisfies Record<Locale, readonly Intl.LDMLPluralRule[]>;

type Plural<L extends Locale> = Record<(typeof PLURAL_CATEGORIES)[L][number], string>;
```

A `pl` catalog entry missing `many` is now a **`tsc` error in `npm run type-check`**, caught before
a test ever runs and impossible to forget for a newly added key. This is the same discipline as the
Python side's `assert_never` — the compiler insists.

### 2. The category table cannot drift from CLDR

The table above is hand-written, so a test asserts it equals
`new Intl.PluralRules(loc).resolvedOptions().pluralCategories` for every locale. If a future CLDR
revision changes a category set, that test fails rather than the table silently lying to the type
system. (`fr`/`it` gained `many` in CLDR 42 — precisely the kind of drift this catches.)

### 3. Golden-number tests pin the traps

`Intl.PluralRules` is correct; our *catalogs* and *call sites* are what break. Every plural key is
rendered at a fixed set of numbers and snapshotted:

| n | `pl` category | Why it is in the set |
|---|---|---|
| 0 | `many` | Zero takes genitive plural — **not** `other`, the classic naive-implementation bug |
| 1 | `one` | |
| 2, 3, 4 | `few` | nominative plural |
| 5, 11, 12, 14 | `many` | 11–14 are `many` despite ending in 1–4 — the second classic trap |
| 22, 23 | `few` | 22 is `few`, not `many` — breaks every `n >= 5 ? many` hand-rolled rule |
| 25, 101 | `many` | |
| 1.5, 2.5 | `other` | **Fractions take genitive singular** — a category that is easy to leave unwritten because integers never reach it |

The `1.5` row is why `other` must never be treated as a synonym for "plural fallback".

### 4. Units bypass the catalog entirely

Do **not** author plural messages for `km`, `m`, or `°C`. Use
`Intl.NumberFormat(locale, { style: 'unit', unit: 'kilometer', unitDisplay: 'short' })` — CLDR
supplies the correct Polish form, including the fractional `2,5 km` case, with no catalog entry to
get wrong. This removes an entire class of breakage from `detailpanel.js:251` and the `°C` sites.

Only genuinely domain nouns need catalog plurals: *pool*, *lane*, *day*, *session*.

### 5. Dates must come from `Intl`, never a month table

Polish dates take a **genitive month**: `20 lipca`, never `20 lipiec` — and weekday/month names are
**lowercase**, unlike German and English. A hand-written `MONTHS` array cannot express this. This is
an additional, independent reason S1 deletes both weekday tables rather than translating them, and
why `board.js`'s space-splitting must die: Polish formatted dates do not tokenize the way English
ones do.

### 6. Authoring rule: no gendered predicates

Polish adjectives and past-tense verbs agree with the subject's gender. Any string that refers to
*the user* in those forms needs a gender `select` — and our gender axis includes `diverse`, for
which Polish has no settled grammatical form.

**Avoid the problem rather than solving it:** phrase all user-referring copy impersonally.
`You're in` → `Możesz wejść` ("one may enter") is genderless; a past-tense or adjectival
construction would not be. This is a review rule on the **English source text**, since the English
author is the one who decides whether a translatable sentence has a gendered subject at all.

### 7. `pl` does not ship on machine translation

DeepL will not reliably pick the plural category or case-inflect an interpolated German proper noun
(`w Hallenbad Bungertwies`). MT is a first pass only; `pl` requires native review before release.
The repo owner is a native speaker, so this is a self-serve gate rather than a hiring problem — but
it is still a required, explicit sign-off, not an assumption.

### 8. `pl` is in the pseudolocale smoke set

The `en-XA` pass finds unexternalized strings. A separate manual pass **in `pl`** finds the ones
that are externalized but wrong — agreement errors, untranslated fallbacks, and layout overflow
(Polish runs longer than English and the ribbon/Gantt labels are width-constrained).

**Pseudolocalization is the gate for everything static analysis cannot see.** Derive an `en-XA`
pseudo-locale from the `en` catalog (accented, ~30% expanded) and smoke the UI: any string still
rendering un-accented is unexternalized. This catches concatenated sentences and API-sourced prose
that no lint rule will.

**No dependency is needed.** Earlier research proposed `@formatjs/cli` for this, but with a
hand-rolled runtime and a typed `en` catalog module, generating `en-XA` is a ~10-line character map
applied at load time behind a dev flag. `eslint-plugin-i18next` is the only new dev dependency this
plan adds.

Note its `mode: 'all'` will be noisy against this DOM-building codebase (`classList.add`,
`setAttribute`, import specifiers all need allowlisting), and the rule's non-JSX behaviour under
eslint 9 flat config is worth a short spike before committing to it. Land it as `warn`, drive to
zero, then flip to `error` in S7.

### QA chain

The gates slot into the existing `qa` script **before `crap`**, preserving the
coverage-writer-then-crap ordering:

```jsonc
"qa": "npm run fmt:check && npm run lint && npm run type-check && npm run test && npm run crap"
```

`lint` covers both directions (hardcoded strings in source, parity within catalogs); the parity
and completeness assertions ride in `test` so they contribute coverage.

## Translation workflow

For 5 locales at **~231 keys** (the scope table's sum), **no TMS initially** — five catalog modules
reviewed by PR keeps `git blame` as the audit trail. Adopt Weblate (gratis Libre plan for FOSS,
genuinely git-native: clones, commits, opens the PR) or self-hosted Tolgee (free, unlimited keys,
in-context editing — valuable for a spatial ribbon/Gantt layout) only when human translators join;
that is also the point to revisit the `.ts`-vs-`.json` catalog decision.

First pass: **DeepL API Free**, 500k chars/month, materially the strongest engine for exactly this
pl/de/fr/it set.

**`pl` never ships on raw MT** — see "Polish cannot be broken" §7.

## Resolved: default locale

**`en` is both the source locale and the default fallback.** Every message key resolves in `en`, so
a missing translation in any other locale degrades to English rather than to a blank or a raw key.
`de` is the first *translated* locale (see Rollout order) but is not privileged in the fallback
chain.

## Resolved: external source links stay German

The intent was to point `catalog.json` `url` fields at `/en/` stadt-zuerich pages where they exist.
**They do not exist for the pool pages.** Verified 2026-07-26 against the Aemtler page:

- the `/en/` path substitution returns **HTTP 404**;
- the `/de/` page declares **no `hreflang`, no language switcher, and no alternate-language links**.

(Evidence is the pool pages specifically — parts of stadt-zuerich.ch do have English content, but
this section is not among them.)

So: **links keep their `/de/` URLs in every locale.** Do not build a rewrite mechanism for pages
that do not exist, and never string-substitute a locale into a URL — that manufactures 404s.

What we do instead is **label the link honestly**. `sourcestrip.js`'s `'Official page'` becomes a
message with an explicit language marker (`Official page (German)`, `Strona oficjalna (po
niemiecku)`), so a Polish or Italian speaker knows before clicking. This matches the project's
existing honesty idiom — telling the user what we actually have rather than implying more.

If English pages ever appear, the online `build-catalog` command records an `url_en` per pool when
one resolves, and the offline `build` merely carries it through. Availability is **discovered, never
assumed** — which also keeps `swimzh build` offline, as required.

## Resolved: holidays

### The problem is smaller than it looked

Ten names, not fifteen — the five school-holiday names never render (see Out of scope). And of the
ten public holidays, only **one** is genuinely untranslatable.

`resolver.py:90-91` is also, itself, another instance of the mixed-language seam this plan exists to
fix: `f"closed ({name})"` wraps a German name in an English sentence, producing
`Closed · closed (Berchtoldstag)`. It becomes a code plus a holiday parameter under S2/S4.

### Holiday identity is a code, not a date

The calendar carries `known_years: [2026]`, so dates change annually while the holidays recur. Key
the message on a **stable holiday code** (`new_year`, `berchtoldstag`, `good_friday`, …) authored
alongside the date in `data/calendar/zurich.yaml`; the German `name` becomes a human-readable
comment rather than the identity.

### Three tiers

| Tier | Holidays | Treatment |
|---|---|---|
| **Shared** (8) | Neujahr, Karfreitag, Ostermontag, Tag der Arbeit, Auffahrt, Pfingstmontag, Weihnachten, Stephanstag | Translate normally — every one has a standard name in all five languages. `Auffahrt` looks Swiss but is merely the Swiss-German word for Ascension, a universal feast. |
| **Descriptive** (1) | Bundesfeier | Not a shared holiday, but a nameable one: *Swiss National Day*, *Fête nationale suisse*, *Święto Narodowe Szwajcarii* — the same way Bastille Day is rendered abroad. |
| **Untranslatable** (1) | **Berchtoldstag** | Swiss/Liechtenstein only; no equivalent concept exists elsewhere. Keep the German name and gloss it — `Berchtoldstag (2 January, Swiss public holiday)`. Do not invent a translation. |

### `fr` and `it` are looked up, not translated

French and Italian are **Swiss national languages**, and the Confederation publishes official
French and Italian names for federal and cantonal holidays. Those names are authoritative — invent
one and you are contradicting an official source, which is the same class of error as breaking a
Polish plural.

**Rule: for `fr`/`it`, source the official Swiss name; only `en` and `pl` involve editorial
judgement.** This is a research task for whoever authors those catalogs, not a translation task, and
it must not be handed to machine translation.

### Names degrade gracefully

The functional information is *"this pool is closed on 2 January"*; the holiday's name is
decoration. So an unnamed or untranslated holiday must still produce a useful sentence:

```
closed_public_holiday      → "Closed · public holiday"           (no name available)
closed_public_holiday+name → "Closed · Berchtoldstag"            (name available)
```

`resolver.py:90`'s existing `ctx.holiday_name or "public holiday"` already has the right instinct —
generalise it per-locale rather than replacing it. A locale that lacks a name for some holiday is
then a cosmetic gap, never a broken or empty label, and an upstream holiday we have never seen
flows through S4's audited unknown-code path.
